What you validate

The tools the application is built with, and the 15 rules every feature must follow so that features built separately fit together. Once validated, /sdlc-work accepts to plan features, and #14, #15, #16 and #18 can start.

Decisions you took in this session

  • No framework and no library in shipped code; test tools allowed (your rule). Rust was excluded by it.
  • Go for the server, over Node/TypeScript (which was recommended).
  • Plain JavaScript without compilation; fake operator in Go; operator CRDs from its published chart; Helm 4.
  • Exposure through Gateway API (your answer), hence login by Kubernetes token; Envoy Gateway on kind.
  • Export in JSON; go-mutesting for Go mutation; short stack rules in AGENTS.md.
  • After review: scaleway-system is reserved too; Instance zone and Scaleway name are frozen after creation; the export holds no Secret, only the names to recreate; re-import only creates; a NamespaceRole is editable only when Validated.

Rules proposed by the architect, not yet seen by you

These close gaps found by the four reviewers. Validating the spine validates them; send it back if one is wrong.

  • AD-4: resources stay raw JSON; an edit sends only the changed fields with the version you saw; if someone changed it meanwhile you get a conflict, never a silent overwrite.
  • AD-5 details: the exported Namespace carries two added annotations (scaleway-manager.mathieubodin.io/export-format and …/required-secrets); an export covers one namespace: Namespace, its NamespaceRole, then its resources.
  • AD-6: a namespace is "managed" only if it has a UUID project-id annotation; the page mirrors the rules from one file tested against the server's own test table.
  • AD-7: one live stream per open page, with a fixed event format and automatic recovery.
  • AD-12: two user roles shipped unbound: one per namespace, one cluster-wide; each feature adds the rights it needs in the same PR.
  • AD-13: one URL scheme and one error format for all features.
  • AD-14: Secret values never reach the browser.
  • Security: protection against cross-site requests on every write (not a delete confirmation), safe rendering of cluster data, strict page headers, token hidden from logs.
