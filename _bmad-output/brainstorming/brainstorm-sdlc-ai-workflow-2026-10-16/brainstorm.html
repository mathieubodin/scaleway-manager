Technique 1

Job to Be Done

For which job is the workflow hired? Fourteen job tickets, each one a reason to hire it.

The workflow is hired so that the author can delegate to an agent without losing track of what was decided.
Make every session findable, so that from GitHub one knows why a piece of code exists.
Prevent an agent session from producing work with no trace, that is, with no item and no cost.
Give the author a receipt per unit of value delivered: what a feature cost in tokens.
Resume interrupted work in a blank session: the context lives in the item, not in the window.
Separate what is decided (human) from what is executed (agent), so that human validation has a named place.
Make cost visible before launching a session (estimated budget per item), not only afterwards.
Stay usable by a solo author, with no team and no heavy ritual.
Apply the throwaway-cluster spirit to working state: all durable state lives off the local machine.
Produce a history readable by a stranger discovering the public repository.
Keep the brainstorm, plan, issue chain from CLAUDE.md without GitHub being the starting point.
Provide a definition of done that an agent can verify.
Make the agent session the natural accounting unit, rather than the PR.
Decide what to stop delegating to the AI, where it costs more than it brings back.

Technique 3

Ship in 60 Minutes

What do we cut, fake or borrow to ship an hour from now?

60 min

Twelve moves sorted into four lanes. The cut lane is struck through on purpose: those things do not exist yet.

Ship

  • Ship first without automation: a hand-filled end-of-session comment template, to validate the form before automating.
  • Ship the workflow first as a single procedure document readable by the agent, before any script.
  • Ship the item, session, PR cycle on one real small task and read what it costs.

Cut

  • Epics at the start: issue and sub-issue only.
  • Milestones, as long as no version is targeted.
  • The Roadmap view, as long as there are no dates.
  • All GitHub Actions automation: everything goes through the gh CLI from the local session.
  • Priority and effort labels while there are fewer than ten items.

Fake

  • Fake the measurement: estimate the cost from the AI tool's usage console, per day, reconciled by hand.
  • Fake granularity: a single session item per day at first, to have numbers before refining.

Borrow

  • The /cost comment template from scaleway-operator, attached to the session rather than the PR.
  • The usage counters shown by the AI tool at session end (to be checked).
  • The planning skills already installed to produce plans, with no new tool written.

Technique 6

Six Thinking Hats

Six successive viewpoints. The white hat holds facts about the current setup (recorded here as insights).

White · facts
  • Project #4 has Status, Priority, Effort, Tokens and the views Overview, Board, Roadmap, Pull requests.
  • In the operator, cost is entered by hand through a /cost comment on the PR and written on each linked issue.
  • main is protected, squash merge only, PR title checked.
Red · gut feeling
  • Manual cost entry is a chore that will be forgotten.
  • A wrong measure is worse than no measure.
Yellow · benefits
  • Knowing what a feature cost helps decide what to delegate to the agent.
  • Traces make the public repository readable to a third party.
Black · risks
  • On a public repository, comments open to everyone can falsify the cost.
  • A personal token with project rights in Actions secrets is an attack surface.
  • Measured cost is incomplete: sessions outside the repo, sub-agents, discarded attempts.
  • Dependence on the AI tool's internal formats, which may change.
Green · new ideas
  • Separate exploration cost (brainstorm, plan) from realisation cost (implementation).
  • A session item type, distinct from the issue and attached to it: a light sub-issue or a structured comment.
Blue · process
  • Decide the item types first, the tools next, the measurement last.

Technique 8

Disney Method

Dreamer, realist, critic: three rooms walked in order.

The Dreamer

  • Every GitHub item creates itself from a conversation, with context, criteria and budget.
  • The project shows live cumulative cost per epic and average cost per task type.
  • The agent proposes the split into sub-issues and estimates its own cost before starting.
  • A table compares planned and actual cost per item.
  • The session ends with a summary published on the item by itself.

The Realist

  • Start with an end-of-session template that the agent fills in and publishes via gh on the item.
  • The Tokens field receives the sum computed by a small local script launched by a hook.
  • Automatic splitting is adopted only after human validation.

The Critic

  • An agent estimating its own cost before acting is probably unreliable. Untested
  • A hook writing to GitHub from the local machine requires a local token: where is it stored?
  • If the session crashes, the cost is lost if it is only written at the end.

Surviving crashes and sub-agents

  • Write the cost incrementally through checkpoints rather than at the end, to survive crashes.
  • A parent session item that groups the sub-agents launched during a session.

Linking code to cost

  • Link code and cost by a session identifier in the PR body, because the squash makes branch commits disappear.
  • The PR body becomes the squashed commit body, and the PR_BODY setting is already active: a Cost section would be kept there.
  • The PR body contains an automatically filled Cost section.
  • The cost of a PR is the sum of the costs of the sessions cited in its body; the PR writes nothing on the issues.

Avoiding double counting

  • Two distinct fields, own cost and cumulative cost, avoid double counting.
  • Or a single own Tokens field, the cumulative being computed at read time by a script.

Views, reports, budgets

  • A cost-per-epic view produced outside GitHub by a script reading the API.
  • A periodic report generated by a workflow: costs per epic, per type, trends.
  • A budget per epic, with overrun flagged in the item.
  • A measurement-debt item listing sessions with no associated cost, to see the coverage of the measure.

Before the issue exists

  • Also count the brainstorm and planning sessions, which precede the issue: their cost attaches to the intent.
  • Correction: in this project brainstorms and plans are committed (everything in _bmad-output/ is versioned), so they exist in Git. Whether their synthesis is also deposited on the GitHub item is a separate, open question.

Synthesis

Six insights drawn from the whole session.

Coach proposals None of these is a decision by the author. They are proposals from the coach.
1
Coach proposal

The accounting unit is the agent session

Not the PR, not the issue. The cost is captured at the source and the aggregates (per item, per epic) are derived by sum, which removes the double counting observed in the operator.

2
Coach proposal

Three item types may suffice

Intent (epic), task (issue), session (carries the cost). Milestone = published version. The seven SDLC phases attach to these types without creating seven.

3
Coach proposal

Traceability rule: no item, no session

The end of a session deposits the decisions on the item. Correction: brainstorms and plans are committed in this project, so they are versioned in Git; depositing their synthesis on the item is a separate, open question.

4
Coach proposalDepends on an unverified fact

Cost automation hangs on one unverified fact

The presence of token counters readable locally in the session log. If absent, fall back to the usage console aggregated by period. Separate the schema (where the cost goes) from the source (where it comes from).

Not verified: whether the session log holds usable token counters.
5
Coach proposal

Security: only the authenticated owner writes the cost

The operator's current workflow does not check the comment author, and a token with project rights in Actions secrets is an attack surface.

6
Coach proposal

Minimal path: write it by hand first

A hand-filled end-of-session template on a single small task, to read a first real cost, then automate.
